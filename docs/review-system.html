Two-Tier Critique with Earned Unlock

The recipe review system: anyone can speak, the instrument is gated, and every verdict carries a confidence weight instead of hitting a wall.

Status: Adopted Scope: recipe posts (discussions use votes) MVP slice: Tier 0 + Tier 1 (M3) · full system M6–M7 2026-08-30
Governing principle. Gate the instrument, not the right to speak. Anyone can leave a verdict; the gate controls (a) whether it enters the scored aggregate and (b) which question set is offered. Recipe review supply is thin — a hard wall kills volume and pushes people to lie past it. A soft gate with a confidence weight gets honest data and keeps supply.

Tier 0 exists to absorb the "haven't made it yet but 3 stars" traffic: give that impulse a legitimate outlet and it stops contaminating ratings. Saves are demand signal, worthless for quality — stored in a separate table entirely. Tier 2 has an internal extension (2b) that unlocks RATA intensity sliders and the modality grid once a user demonstrates calibration; same schema, richer values, not a separate tier in the data model.

2Field specification

Tier 1 — Verdict MVP · M3

Three inputs, one screen, no scrolling.

make_again   bool                                      required
fidelity     enum(as_written|minor_change|major_change) required
outcome      enum(worked|failed)                        required
note         text ≤280                                  optional
photo        media                                      optional
  • outcome is separate from make_again on purpose: "it worked and I don't want it again" and "it failed and I'll retry" are both common and both meaningful.
  • If fidelity != as_written: show the ingredient list as tappable chips to capture swaps. Chips are 3 seconds and produce structured data; free text is 30 seconds and produces a parsing problem.
  • If outcome == failed: branch straight to the execution block and skip hedonic questions. Asking how much someone liked a broken sauce is noise.

Tier 2 — Cook's Report Phase 2 · M7

3The gate: two independent mechanisms

Most designs get this wrong by merging them. They answer different questions with different evidence.

Gate A — per-review eligibilityGate B — per-user capability
QuestionDid this person cook this recipe on this occasion?Has this account demonstrated calibrated reporting?
ScopeOne review. Recomputed per submission. Never inherited.The account. Slow-moving.
Outputcook_confidence ∈ [0,1]instrument_level ∈ {verdict, report, calibrated}

A first-time user with a perfect cook session passes Gate A at 0.9 and still gets Tier 1 only (Gate B hasn't cleared). A calibrated veteran reviewing a recipe they didn't cook fails Gate A and gets Tier 0. Both are correct behavior.

4Gate A: cook-confidence scoring

Logistic model over evidence signals. Hand-set priors below, recalibrated against a labeled audit set once one exists — not final numbers.

gate_a:
  tier1_scoring_floor: 0.35   # below: review displays, weight = 0
  tier2_offer_floor:   0.65   # below: Tier 2 is not offered
  audit_flag_ceiling:  0.20   # below: queue for review
  session_ttl_hours:   72     # Tier 2 window closes after this
# config, not constants — and NEVER published to clients
  • Retroactive claim path (the MVP's primary path): claim the cook, attach a photo, answer 2–3 outcome-variance questions derived from the recipe ("did the dough come together in the stated 8 minutes?"). No lookup-able correct answer — we check internal consistency, not grade a quiz. Grants a ceiling of ~0.55: passes Tier 1 scoring, never Tier 2.
  • Multi-session cooks: sessions pause, resume, and span days; compute time bands against total elapsed with active-work carve-outs, or every bread recipe auto-fails.
  • Category-specific bands: a cocktail is 90 seconds, a braise is 4 hours. Store expected_active_minutes / expected_total_minutes per recipe; derive bands from category distributions, not global ones.
  • Retroactive recompute: confidence is not frozen at write time. Reliability shifts and late pHash matches trigger recompute and re-aggregation. Confidence is a versioned field carrying its model version.

5Gate B: instrument unlock Phase 2 · M7

gate_b:
  report:                        # unlocks Tier 2
    verified_cooks_lifetime: 3   # each at cook_confidence ≥ 0.65
    distinct_recipes: 3
    account_age_days: 7
    moderation_strikes: 0
  calibrated:                    # unlocks 2b (RATA + modality grid)
    completed_reports: 10
    consensus_agreement: ≥ 0.6   # rank correlation vs settled profile
    jar_variance: ≥ threshold    # rejects "just right to everything"
    calibration_exercise: passed # optional, cheap, high-yield
  • jar_variance is a straggler filter: a user whose JAR responses are 95% zeros isn't perceiving, they're clicking through. Don't hand them intensity sliders.
  • calibration_exercise: rate three reference items with known consensus profiles; store a per-user scale-usage correction. Teams that skip this get users who never touch the ends of any scale and no way to normalize it out.
  • Unlocks never expire, but scores degrade: if consensus agreement drops below floor over a rolling 20 reports, demote to report silently. Nothing generates gaming faster than a visible status you can lose.

Tier 2 is invitational, not requestive — a post-cook prompt the evening of the session, never a form buried in the recipe page. Prompted completion runs several multiples of self-initiated. Findable if sought, but not the designed path.

7Weighting into the aggregate

w = cook_confidence × user_reliability × recency_decay

Tier is not a term in the equation. Tier is a UI construct; the epistemic content is already in cook_confidence. A tier multiplier double-counts and can hand a suspicious Tier 2 report more weight than a clean Tier 1 verdict.

  • Aggregate make_again with a weighted Wilson lower bound (or beta-binomial against a category prior). Publish n. Never a raw proportion. Public display: "92% would make again (n=41)" — no stars anywhere on the platform.
  • as_written → full weight to canonical · minor_change → full weight, swap logged as variant annotation · major_change → weight 0 on canonical; forks or attaches to a variant node.

8Anti-gaming

  • Never publish thresholds — not in docs, UI, or error copy. "Not enough signal from this cook" is the whole message.
  • Per-user threshold jitter (±0.03) so behavior can't be reverse-engineered by A/B'ing your own account.
  • Rate-limit verified cooks per user per day; nobody legitimately completes nine cook sessions on a Tuesday.
  • Cross-account correlation: shared device fingerprints, identical timing, synchronized starts. Ring detection matters more than individual fraud.
  • Fraud economics: price a fake Tier 2 report before hardening further. If nobody profits, bad data is laziness, and laziness is the jar_variance filter's job.

9The built-in bias, and the mitigation

Gating on completed cooks creates survivorship bias: abandoners never review, so the verified pool over-represents successes and hides recipes that are confusing, badly timed, or fail silently. Mitigation — and genuinely novel data nobody else has — instrument the abandonment. Session started but never completed → one-question prompt the next day:

abandon_reason    enum(ran_out_of_time | missing_ingredient |
                       step_unclear | technique_failed |
                       changed_plans | equipment_issue)
abandoned_at_step int

step_unclear and technique_failed bucketed by step index tell an author more than a hundred glowing reviews. This is a Tier 1-class artifact: weighted and displayed as one.

11Copy per gate state

Tone rule: the gate never accuses. It describes what's missing and offers the next step.

Passed, Tier 2 offered — "You cooked this Tuesday. Got 90 seconds to help the next person?"
Passed Gate A, Gate B not met — "Thanks. After a couple more cooks you'll be able to leave a full report."
Retroactive claim — "Didn't have the app open? No problem, answer a couple of questions about how it went."
Below scoring floor — "Saved your note. It'll show on the recipe, but it won't count toward the rating until we can confirm the cook."
Tier 0 — "Saved. Rate it once you've made it."

Never write "verified cook" as a status to pursue — write it as something that happens to the user. The moment it reads as a badge to chase, people chase it.

12Platform integration (smoodie)

Amendments adopted for smoodie. (1) Web-first v0: MVP is a web app, so the strongest provenance signals (in-app camera, session telemetry) don't exist yet — the retroactive-claim path is the primary MVP path and v0 confidence weights lean on photo, account age, timing, and the ~0.55 claim ceiling. (2) Recipe versioning: authors edit recipes; reviews pin recipe_version at claim time, and cross-version weight is annotated in the aggregate. (3) Non-recipe posts: this system is recipe-only — discussion posts and comments use upvote/downvote. (4) Display metric: the public score is the weighted Wilson "% would make again (n)" everywhere; stars appear nowhere.
